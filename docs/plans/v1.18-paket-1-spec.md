## 1. Ziel

Den Katalog-Datenvertrag zwischen der App (`EpisodeTracker`) und dem Katalog-Repo
(`Digi951/hoerspiel-kataloge`) verbindlich festschreiben und die neuen optionalen
Felder additiv im App-Code verankern, **ohne** sie schon in der UI zu nutzen
(das ist Paket 3/4). Das Prüf-Kriterium aus §8 ist:

> **Fixture-Validierung, V1.17-Decoding**

Konkret liefert Paket 1:

1. Ein **Contract-Dokument** `docs/catalog-data-contract.md`, das Legacy- und
   V2-Format Feld für Feld beschreibt: Statusregeln, IDs, Quellen- und
   Revisionsfelder, Terminfeed-Format.
2. **Struct-Änderungen** in `CatalogEntry`, `CatalogParser.CatalogDocument`,
   `CatalogManifest` / `ManagedCatalogSource` und `UpcomingRelease` /
   `UpcomingReleasesDocument`: neue Felder per `decodeIfPresent` lesen, im
   Cache-Roundtrip erhalten, sonst verhaltensneutral.
3. **JSON-Fixtures** (synthetisch) + Decoder-Toleranztests, die beweisen:
   - heutiger App-Code liest V2-Kataloge/-Feed ohne Verlust,
   - ein „1.17-Decoder" (die eingefrorenen Struct-Definitionen vor dieser
     Änderung, als Testdouble) liest V2-Daten ohne Absturz — unbekannte Felder
     werden ignoriert, unbekannte Feed-Zeilen still übersprungen.
4. **Generatorweg**: Anpassungs-Spezifikation und konkrete Patches für
   - den Scheduled Task `hoerspiel-katalog-check` (`~/.claude/scheduled-tasks/hoerspiel-katalog-check/SKILL.md`),
   - `hoerspiel-kataloge/scripts/check_catalogs.py`,
   damit beide das V2-Format erzeugen bzw. validieren. Umsetzung im Katalog-Repo
   erfolgt in einem eigenen Commit / PR gegen `Digi951/hoerspiel-kataloge`, in
   diesem Paket mitgeplant und referenziert.

## 2. Nicht-Ziele (bewusst außerhalb Paket 1)

- Keine UI, die `releaseStatus` / `releaseDate` / `changedAt` anzeigt (Paket 3/4).
- Kein Neuigkeiten-Store, keine Delta-/Baseline-Logik (Paket 4).
- Kein SchemaV9, keine `Universe.managedCatalogID`-Bindung (Paket 3).
- Keine echten FR-Pilotdaten — nur synthetische Fixtures. Die Pilotdaten-Hälfte
  von Paket 1 hängt an Paket 0 (Rechteklärung, offen) und wird nachgezogen,
  sobald die zwei FR-Kataloge stehen (zweiter Fixture-Durchlauf, kein
  Vertrags-Blocker).
- Kein separater V2-Terminfeed (`upcoming_releases_v2.json`) — siehe §5.4.
- Keine Migration der bestehenden Katalog-JSON von Legacy → V2 in großem Stil;
  der Vertrag beschreibt beide, die Umstellung erfolgt schrittweise durch den
  Nutzer / künftige Läufe.

## 5. Der Datenvertrag (Inhalt von `docs/catalog-data-contract.md`)

### 5.1 Manifest (`manifest.json`)

| Feld | Typ | Pflicht | Bedeutung / Regel |
|---|---|---|---|
| `schemaVersion` | Int | **ja** | Aktuell `1`. Nicht-optional im 1.17-Decoder → darf nie entfernt werden. Erhöhen nur bei nicht-additiver Manifest-Änderung. |
| `updatedAt` | String (`yyyy-MM-dd`) | nein | Redaktioneller Stand. |
| `catalogs[]` | Array | ja | siehe unten |
| `catalogs[].id` | String | ja | Stabile, eindeutige Kennung (kebab-case). Umbenennungen ändern `id` nicht. |
| `catalogs[].name` | String | ja | Anzeigename, **stabil für Legacy-Clients** (namensbasiertes Matching). |
| `catalogs[].language` | String (ISO-639-1) | nein | Default `"de"`. App filtert Manifest nach Gerätesprache. |
| `catalogs[].style` | String | nein | `numbered` (Default) \| `anthology`. Unbekannt ⇒ `numbered`. |
| `catalogs[].url` | String (URL) | ja | GitHub-raw-URL der Katalogdatei. |

### 5.2 Katalogdatei (`catalogs/<lang>/<slug>.json`)

Wrapper-Doc. Flat-Array (`[entry, …]`) bleibt als Legacy-Eingang gültig, wird
aber nicht mehr empfohlen.

| Feld | Typ | Pflicht | Bedeutung / Regel |
|---|---|---|---|
| `collectionName` | String | empfohlen | Fällt sonst auf den Manifest-`name` zurück. |
| `version` | Int | empfohlen | Grobe Katalog-Revision. Monoton steigend bei jeder redaktionellen Änderung. Von der App als `CatalogSnapshot.version` / Delta-Basis genutzt. |
| `lastUpdated` | String (`yyyy-MM-dd`) | empfohlen | Redaktioneller Stand. |
| `entryCount` | Int | nein | Nur Konsistenz-Hinweis; App verlässt sich auf `entries.count`. |
| `catalogFormat` | Int | nein | `1` (Legacy) \| `2` (V2). Fehlt ⇒ `1`. Intent-Marker (D8). |
| `entries[]` | Array | ja | siehe 5.3 |

### 5.3 Katalogeintrag (`entries[]`)

| Feld | Typ | Pflicht | Legacy | V2 | Regel |
|---|---|---|---|---|---|
| `number` | Int | bei `kind:regular` in `numbered` | ✓ | ✓ | Laufende Folgennummer. Bei `style:anthology` **weglassen**. |
| `kind` | String | nein (Default `regular`) | ✓ | ✓ | `regular` \| `special`. Bei `style:anthology` **muss** jeder Eintrag `special` sein (Invariante wird beim Import erzwungen — Paket 2b). |
| `slug` | String | bei `kind:special` **ja**; bei `anthology` **ja** | ✓ | ✓ | Stabile Identität ohne Nummer. kebab-case, eindeutig im Katalog. |
| `title` | String | **ja** | ✓ | ✓ | Anzeigetitel. |
| `releaseYear` | Int | nein (Default `0` = unbekannt) | ✓ | ✓ | `0` bleibt „unbekannt", wird nie geraten. |
| `collectionName` | String | nein | ✓ | ✓ | Überschreibt den Doc-Wert pro Eintrag (Sammel-Kataloge). |
| `links` | Object `{string: string(URL)}` | nein | – | ✓ | Keys: `spotify`/`apple`/`deezer`/`audible`/`audioteka`/`storytel` (= `StreamingService.rawValue`) **plus** reservierter Key **`source`** für eine generische Originalquelle (Sender-Mediathek, Studio-Seite). Leere/Whitespace-Werte werden entfernt. |
| `spotifyURL` / `appleMusicURL` / `deezerURL` / `audibleURL` | String (URL) | nein | ✓ | – (deprecated) | Legacy-Flachfelder. Weiterhin **gelesen** und in `links` gemappt; explizite `links`-Einträge gewinnen. Nicht mehr schreiben in V2. |
| `releaseDate` | String (`yyyy-MM-dd`) | nein | – | ✓ | Kalendertag der Veröffentlichung. Verankerung wie Feed (lokale Mitternacht). Nur setzen, wenn belastbar bekannt. |
| `releaseStatus` | String | nein (Default `unknown`) | – | ✓ | `announced` \| `released` \| `unknown`. `unknown` nie zu `released` umdeuten. Legacy-Einträge ohne Feld bleiben `unknown` und voll nutzbar. |
| `sourceCheckedAt` | String (`yyyy-MM-dd`) | nein | – | ✓ | Datum, an dem `links.source` zuletzt redaktionell geprüft wurde. |
| `changedAt` | String (`yyyy-MM-dd`) | nein | – | ✓ | Datum der letzten inhaltlichen Änderung dieses Eintrags. Basis für Neuigkeiten-Deltas (Paket 4). |

**Statusregeln (normativ):**

1. Fehlt `releaseStatus`, gilt `unknown`. `unknown`-Einträge sind vollwertig
   (Bibliothek, Statistik, Autocomplete) — sie sind nur nicht „erschienen".
2. Ein Eintrag mit `releaseStatus: announced` und `releaseDate` in der
   Zukunft ist ein Terminkandidat (Feed-Projektion, §5.4).
3. Ein Eintrag mit `releaseStatus: announced` und `releaseDate` in der
   Vergangenheit bleibt `announced` (nicht automatisch `released`) → UI zeigt
   „unbestätigt" (Paket 4). Der Generator darf ihn bei belegter
   Veröffentlichung auf `released` heben.
4. `releaseDate` ohne `releaseStatus` ⇒ Status bleibt `unknown`, das Datum ist
   rein informativ.
5. Terminverschiebung: `releaseDate` ändern **und** `changedAt` auf heute
   setzen. Kein eigener `delayed`-Status in V1.18.

### 5.4 Terminfeed (`upcoming_releases.json`)

| Feld | Typ | Pflicht | Bedeutung / Regel |
|---|---|---|---|
| `feedVersion` | Int | nein (Default `1`) | Fluchtweg-Marker (D3). `1` = additiv erweitert; ein künftiger echter Bruch führt `2` + separate Datei ein. |
| `updatedAt` | String (`yyyy-MM-dd`) | nein | Lauf-Datum. |
| `releases[]` | Array | ja | Datei wird bei jedem Lauf vollständig ersetzt. |
| `releases[].catalogID` | String | **ja** | = Manifest-`id`. |
| `releases[].number` | Int | bei `numbered`-Serien ja; bei `anthology` **weglassen** | War bisher Pflicht. Jetzt optional. |
| `releases[].slug` | String | bei `anthology` **ja** | Identität ohne Nummer. |
| `releases[].title` | String | **ja** | |
| `releases[].releaseDate` | String (`yyyy-MM-dd`) | **ja** | Angekündigter Termin. |
| `releases[].releaseStatus` | String | nein (Default `announced`) | Im Feed praktisch immer `announced`; `released` sobald belegt (dann fällt die Zeile beim nächsten Lauf raus). |

**Kompatibilität:** Ein 1.17-Client dekodiert jede Zeile durch
`LenientRelease` → `try?`. Eine Zeile ohne `number` (Anthologie) wirft in
`UpcomingRelease.init(from:)` (dort ist `number` nicht-optional) und wird von
`LenientRelease` still verworfen — der 1.17-Client zeigt sie nicht an, stürzt
aber nicht ab. Zusätzliche unbekannte Felder (`slug`, `releaseStatus`,
`feedVersion`) werden vom synthetisierten Decoder ignoriert.

### 5.5 ID-Referenz (Zusammenfassung)

| Ebene | Stabile Identität | Anzeige-/Legacy-Identität |
|---|---|---|
| Katalog | `manifest.catalogs[].id` | `name` |
| Eintrag `numbered/regular` | `number` (im Katalog) | `number` |
| Eintrag `special` / jede `anthology`-Folge | `slug` (im Katalog) | `title` |
| Terminzeile | `catalogID` + (`number` ?? `slug`) | `title` |

## 6. App-Änderungen (dieses Repo)

### 6.1 `CatalogEntry` (`Features/Catalog/CatalogModels.swift`)

- Neue gespeicherte Properties: `releaseDate: Date?`, `releaseStatus: CatalogReleaseStatus`
  (neues Enum, Default `.unknown`), `sourceCheckedAt: Date?`, `changedAt: Date?`.
- `CatalogReleaseStatus`: `enum … : String, Codable, Sendable { case announced, released, unknown }`
  mit `init(from:)`, das unbekannte Rohwerte auf `.unknown` mappt (analog
  `CatalogStyle.resolve`) — kein Decode-Fehler bei einem neuen Serverwert.
- `CodingKeys` + `init(from:)`: `decodeIfPresent` für alle vier (Datumsfelder
  über einen gemeinsamen `yyyy-MM-dd`-`DateFormatter`, aus `UpcomingRelease`
  extrahiert nach `Shared/`), `releaseStatus` über `decodeIfPresent(String) ?? "unknown"` → Enum.
- `encode(to:)`: die vier Felder mit `encodeIfPresent` schreiben, damit der
  Disk-Cache sie erhält (`CatalogCacheStore` serialisiert `[CatalogEntry]`).
- Beide `init(...)`-Convenience-Overloads um die vier neuen Parameter mit
  Default `nil` / `.unknown` erweitern (Aufrufer + Tests kompilieren unverändert).
- Kein Verhalten an `hasStreamingLink`, `preferredLink`, `sourceURL` ändern.

### 6.2 `CatalogParser.CatalogDocument` (`Features/Catalog/CatalogParser.swift`)

- `catalogFormat: Int?` ergänzen (`decodeIfPresent`), in
  `NormalizedCatalogDocument` durchreichen. Kein Verhalten daran hängen —
  nur verfügbar machen (Validator/Debug).
- Die `entries.map { CatalogEntry(number: … links: …) }`-Neuaufbauten in
  `parseCatalogEntries` / `parseNormalizedCatalogDocument` müssen die vier
  neuen Felder mit-durchreichen (sonst gehen sie beim Normalisieren verloren).

### 6.3 `ManagedCatalogSource` / `CatalogManifest`

- Keine Struct-Änderung nötig (`style` ist schon optional). Nur Contract-Doku.
- Optional (nice-to-have, kein Muss für das Gate): `CatalogManifest.updatedAt`
  bleibt wie es ist.

### 6.4 `UpcomingRelease` / `UpcomingReleasesDocument` (`Features/Catalog/UpcomingRelease.swift`)

- `number: Int` → `number: Int?`.
- `slug: String?` ergänzen.
- `releaseStatus: CatalogReleaseStatus` ergänzen (Default `.announced` im Feed-Kontext;
  Rohwert-tolerant).
- `id`: `"\(catalogID)-\(number)"` → `"\(catalogID)-\(number.map(String.init) ?? slug ?? "?")"`.
- `init(from:)`: `number` per `decodeIfPresent`; **Validierung**: entweder
  `number` **oder** `slug` muss vorhanden sein, sonst
  `DecodingError.dataCorrupted` (damit `LenientRelease` sie verwirft statt eine
  id-lose Zeile durchzulassen).
- `UpcomingReleasesDocument`: `feedVersion: Int?` (`decodeIfPresent`).
- `UpcomingReleasesFeed` (`Features/Catalog/UpcomingReleasesFeed.swift`):
  `.filter { activeCatalogIDs.contains($0.catalogID) && $0.releaseDate >= startOfToday }`
  und `.sorted { ($0.releaseDate, $0.number) < … }` — `number` ist jetzt
  optional; Sortierung auf `($0.releaseDate, $0.number ?? Int.max, $0.slug ?? "")`
  umstellen. **Rein mechanisch, kein UI-Redesign** (Anthologie-Zeilen zeigt erst
  Paket 4/5 sinnvoll an; hier nur nicht abstürzen / stabil sortieren).

### 6.5 Gemeinsamer Datums-Helfer

- `UpcomingRelease.dayFormatter()` (private) nach
  `Shared/…/CalendarDayFormatter.swift` (o. ä.) ziehen, als `enum` mit
  `static let shared: DateFormatter` + `date(from:)` / `string(from:)`.

  eine Verankerung. Playbook „Tested Solutions" §`decodeIfPresent`-Regel

## 11. Risiken / offene Fäden

- **Pilotdaten (Paket 0)**: synthetische Fixtures jetzt, zweiter Durchlauf mit
  zwei echten FR-Anthologie-Katalogen sobald Rechteklärung steht. Kein
  Vertrags-Blocker, aber die FR-Datenabnahme (§ Release-Plan „Katalog-Abnahme (FR)")
  bleibt offen bis dahin.
- **`UpcomingReleasesFeed`-Sortierung**: Umstellung auf optionale `number` ist
  mechanisch, aber von `EpisodeListView` / `IPadEpisodeListView` konsumiert —
  Snapshot-Test der Sortierreihenfolge mit gemischten Zeilen absichern.
- **`feedVersion`-Fluchtweg**: falls Paket 4/5-Tests einen echten 1.17-Bruch
  zeigen (nicht nur eine verworfene Zeile), greift D3-Fallback: `feedVersion: 2`
  + separate Datei. Dann ist der Scheduled Task Schritt 1 erneut anzufassen.
- **`check_catalogs.py`**: wird von keinem CI ausgeführt (kein Workflow), nur
  manuell / im Scheduled Task. Änderung dort ist niedrig-risikoreich, aber auch
  nicht test-abgedeckt — Sichtprüfung eines Laufs gegen einen V2-Fixture-Katalog.
