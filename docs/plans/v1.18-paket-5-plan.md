## P5-A — FR als Xcode-Lokalisierung

**Dateien:** `EpisodeTracker.xcodeproj/project.pbxproj`,
`EpisodeTracker/fr.lproj/InfoPlist.strings` (neu).

- `knownRegions = (de, Base, en)` → `(de, Base, en, fr)`. Kleiner,
  gezielter `pbxproj`-Edit (wie Paket 4s Localizable.xcstrings-Ergänzungen:
  Python-Skript, das nur die eine Zeile ändert, kein Re-Serialisieren der
  gesamten Datei — Xcodes eigenes Format ist strikt, ein `json`/generisches
  Tool würde die Struktur zerstören).
- Neues `EpisodeTracker/fr.lproj/InfoPlist.strings`:
  ```
  CFBundleDisplayName = "AudioPlayLog";
  CFBundleName = "AudioPlayLog";
  ```
  (D1 — internationale Marke, wie `en.lproj`, keine Übersetzung des Namens.)
- **Kein** `EpisodeTrackerWidgets/fr.lproj` (D2 — bewusste Nicht-Entscheidung,
  im Spec begründet; betrifft DE/EN gleich mit und ist außerhalb des
  Pakets).
- Test: kein XCTest möglich für Xcode-Projekteinstellungen selbst: Prüfung
  ist ein grüner Build beider Schemes (Debug reicht hier, Release folgt in
  P5-F) plus eine Sichtprüfung, dass `fr` unter „Project → Info →
  Localizations" auftaucht (`xcodebuild -showBuildSettings` oder ein Blick
  in die `.pbxproj`).

## P5-B — Vollständige FR-Übersetzung

**Dateien:** `EpisodeTracker/Localizable.xcstrings`.

- Ein Python-Skript (Muster aus Paket 4 P4-E: gezielte Textblock-Einfügung,
  kein vollständiges Neu-Dump, um Formatierungs-Diff zu minimieren) ergänzt
  für **jeden** der 384 Bestandsschlüssel (plus die in Paket 3/4
  hinzugekommenen, bereits `en`-vollständigen Schlüssel — keine zusätzliche
  Lücke seit dem letzten Sweep) einen `"fr": {"stringUnit": {"state":
  "translated", "value": "…"}}`-Eintrag.
- Platzhalter (`%@`, `%lld`, `%1$@` etc.) müssen 1:1 in Anzahl und Reihenfolge
  wie in `de`/`en` vorkommen — ein Nachlauf-Skript zählt Format-Specifier
  pro Sprache und schlägt fehl, wenn `fr` von `de`/`en` abweicht (verhindert
  einen Crash durch fehlenden/vertauschten Parameter zur Laufzeit).
- `.One`/`.Many`-Paare (z. B. `CatalogUpdate.NewEpisodes.Title.One/.Many`)
  bekommen jeweils eigene, grammatisch korrekte FR-Formen (Französisch
  kennt Singular/Plural wie Deutsch — kein neuer CLDR-Fall nötig).
- Test: kein inhaltlicher XCTest für Übersetzungsqualität möglich (das ist
  gerade die im Spec §6 benannte Lücke). Automatisiert geprüft wird nur die
  **Struktur**: JSON-Validität, Platzhalter-Konsistenz (siehe oben),
  Vollständigkeit (kein Schlüssel ohne `fr`). Ein neues, kleines Skript
  (`scripts/verify-xcstrings-fr.py` oder inline in der Commit-Prüfung, kein
  dauerhaft im Repo laufender Test) reicht dafür — kein XCTest-Ziel nötig,
  da es kein Swift-Code ist, den die App zur Laufzeit ausführt.

## P5-D — FR-Anthologie-Testfixture + Pipeline-Tests

**Dateien:** `EpisodeTrackerTests/Fixtures/catalog_fr_anthology_fixture.json`
(neu), `EpisodeTrackerTests/CatalogFRAnthologyFixtureTests.swift` (neu,
oder Erweiterung von `CatalogDataContractTests.swift`).

- Fixture: 4–6 klar erfundene FR-Anthologie-Einträge (`style: anthology`,
  `kind: special`, `slug`-Identität, mindestens ein Eintrag mit `links.
  source` statt eines Streaming-Diensts, gemischte `releaseStatus`).
  Kopfkommentar im JSON/Test macht unmissverständlich klar: Testdaten, keine
  echten Werke/Studios.
- Tests:
  - Dekodiert unter dem eingefrorenen Paket-1-Datenvertrag (analog
    `CatalogDataContractTests`).
  - `CatalogStyleReconciler`/Import-Konsistenzregel (Paket 2b): jede
    dekodierte Folge hat `kind: special`.
  - `links.source` löst die generische "Originalquelle öffnen"-Aktion aus
    (bestehende Detail-Link-Ansicht, kein neuer Code — nur ein Test mit
    FR-Daten statt der bisherigen DE-Fixtures).
  - Aktivieren (`CatalogActivationHandler`, Paket 3) bindet eine Sammlung an
    die FR-Fixture-Quelle wie an jede andere.
  - Ein simulierter Delta gegen das Fixture erzeugt genau eine `NewsEvent`
    (Paket 4, `NewsReconciler`) — beweist, dass die Neuigkeiten-Pipeline
    Anthologie-Identität (Slug statt Nummer) korrekt trägt.
- **Kein** neuer Produktionscode in diesem Commit — reine Testabdeckung
  gegen bestehende Paket-1/2b/3/4-Infrastruktur mit neuen (FR-)Daten.

## Reihenfolge-Hinweise

P5-A ist unabhängig von allem anderen und kann zuerst laufen. P5-B braucht
P5-A nicht zwingend, aber inhaltlich sinnvoll danach (FR ist als Lokalisierung
"da", bevor sie befüllt wird). P5-C ist eine Doku-Begleitung zu P5-B und läuft
direkt danach. P5-D und P5-E sind voneinander unabhängig und brauchen weder
P5-A/B/C (sie testen Katalog-/Datenlogik, keine UI-Strings) — könnten
parallel zu B/C laufen, werden hier aber danach eingeordnet, weil sie
inhaltlich auf "FR ist jetzt eine echte Sprache in der App" aufbauen. P5-F
letzter Schritt wie gewohnt.
