## 0. Geltungsbereich und Reihenfolge

Der „Generator" ist **kein Skript in diesem Repo**. Er besteht aus zwei Teilen
außerhalb von `EpisodeTracker`:

| Teil | Ort | Rolle |
|---|---|---|
| Scheduled Task `hoerspiel-katalog-check` | `~/.claude/scheduled-tasks/hoerspiel-katalog-check/SKILL.md` (Cron `0 9 * * 1`) | **Schritt 1** erzeugt + committet + pusht `upcoming_releases.json` vollautomatisch. **Schritte 2–5** geben nur einen Report mit Patch-Vorschlägen aus — Katalogdateien ändert der Nutzer von Hand. |
| `check_catalogs.py` | `Digi951/hoerspiel-kataloge` → `scripts/check_catalogs.py` | Link-Health-Checker. Von keinem CI ausgeführt, nur manuell / vom Task referenziert. |

**Umsetzung erfolgt NICHT in diesem Branch.** Nach Abnahme der App-Seite (Paket 1
Gate) werden die Änderungen ausgeführt als:

1. Ein Edit an der Task-SKILL.md (lokal, kein Repo).
2. Ein eigener PR gegen `Digi951/hoerspiel-kataloge` für `check_catalogs.py`.

Die Katalog-JSON selbst wird **nicht** in großem Stil migriert (Vertrag §1
Regel 2): beide Formate bleiben gültig, neue/angefasste Einträge wandern
schrittweise nach V2.

### 1.2 Anthologie-Hinweis ergänzen

Direkt unter dem JSON-Block (nach dem `updatedAt`/`releaseDate`-Satz):

```diff
 `updatedAt` ist das heutige Datum, `releaseDate` das angekündigte Datum, beide
 als `yyyy-MM-dd`. Findet sich keine passende Ankündigung, schreibe
 `"releases": []` — die Datei wird bei jedem Lauf vollständig ersetzt, alte
 Einträge müssen nicht aufgeräumt werden.
+
+Alle in der Tabelle oben gelisteten Serien sind nummeriert — `number` ist dort
+Pflicht. Für eine `anthology`-Serie (keine laufende Nummer) stattdessen `slug`
+statt `number` setzen (kebab-case, stabil, eindeutig im Katalog). Die
+play-europa-Vorschau listet keine Anthologie-Serien, daher ist dieser Fall hier
+aktuell nicht relevant; die Zeile ist der Vollständigkeit halber dokumentiert.
+Eine Zeile ohne `number` **und** ohne `slug` ist ungültig und wird von der App
+verworfen.
```

`feedVersion: 1` bleibt statisch, solange der Feed additiv bleibt. Zeigt ein
Paket-4/5-Test einen echten 1.17-Bruch (nicht nur eine verworfene Zeile), greift
der Vertrags-Fluchtweg D3: `feedVersion: 2` **plus** eine separate Datei
`upcoming_releases_v2.json`, der V1-Feed wird weiter erzeugt. Das ist eine
spätere, bewusste Änderung an diesem Schritt.

## 2. `SKILL.md` — Schritt 5 (Report „Empfohlene JSON-Patches")

Die Patch-Vorlage im Report muss V2 erzeugen: `links`-Objekt statt Flach-URLs,
`changedAt`, `releaseStatus`, bei Sonderfolgen `slug`. Der Report-Block in
Schritt 5:

```diff
 ## Empfohlene JSON-Patches
-[Für jede neue Folge: vollständiger JSON-Eintrag, bereit zum Einfügen in den Katalog]
+[Für jede neue Folge: vollständiger JSON-Eintrag im V2-Format (siehe Vorlage unten),
+ bereit zum Einfügen in `entries[]`. Zusätzlich den Hinweis, `catalogFormat: 2`
+ und ein erhöhtes `version` im Dokumentkopf zu setzen, falls die Datei noch
+ Legacy ist.]
+
+V2-Eintrags-Vorlage (Felder weglassen, die unbekannt sind — nichts raten):
+
+```json
+{
+  "number": 242,
+  "title": "Titel der Folge",
+  "releaseYear": 2026,
+  "links": {
+    "spotify": "https://open.spotify.com/album/…",
+    "apple": "https://music.apple.com/de/album/…",
+    "audible": "https://www.audible.de/pd/…",
+    "source": "https://www.example-sender.de/…"
+  },
+  "releaseDate": "2026-10-15",
+  "releaseStatus": "announced",
+  "sourceCheckedAt": "<heute>",
+  "changedAt": "<heute>"
+}
+```
+
+Regeln für die Vorlage:
+- `releaseStatus`: `announced`, solange die Folge nur angekündigt ist; `released`,
+  sobald ein Streaming-Link belegt erreichbar ist. Nie `unknown` in einem frisch
+  erzeugten Patch.
+- `releaseDate` nur setzen, wenn ein belastbarer Termin bekannt ist.
+- `changedAt` = heutiges Datum (jede inhaltliche Änderung setzt es neu).
+- `sourceCheckedAt` = heutiges Datum, wenn `links.source` gerade geprüft wurde.
+- Sonderfolge ohne laufende Nummer: `"kind": "special"` + `"slug": "<kebab-case>"`
+  statt `number`.
+- Legacy-Flachfelder (`spotifyURL` etc.) **nicht** mehr erzeugen.
```

Schritt 2 („letzten regulären Eintrag … ohne kind=special") und Schritt 4
(Stichprobe tote URLs) bleiben inhaltlich gültig. Einzige Anpassung in Schritt 4:
die zu prüfende URL steht in V2 unter `links.audible`, in Legacy weiter unter
`audibleURL` — beide Orte lesen (`entry["links"]["audible"]` mit Fallback auf
`entry["audibleURL"]`).

## 3. `check_catalogs.py` — `links`-Objekt + `source` verstehen

Der Checker liest heute nur die vier Legacy-Flachfelder (`URL_FIELDS`, Zeile 30).
Er muss zusätzlich das `links`-Objekt lesen, den reservierten `source`-Key auf
Erreichbarkeit prüfen (aber nicht auf Titel), und Legacy weiter unterstützen
(Union), damit gemischte Kataloge während der Umstellung sauber durchlaufen.

### 3.1 Feld-Definitionen ersetzen

```diff
-URL_FIELDS = ["spotifyURL", "appleMusicURL", "deezerURL", "audibleURL"]
-FIELD_LABELS = {
-    "spotifyURL": "Spotify",
-    "appleMusicURL": "Apple Music",
-    "deezerURL": "Deezer",
-    "audibleURL": "Audible",
-}
+# Legacy-Flachfelder → V2-links-Key. Werden weiter gelesen (Union), damit
+# gemischte Kataloge während der Umstellung durchlaufen.
+LEGACY_URL_FIELDS = {
+    "spotifyURL": "spotify",
+    "appleMusicURL": "apple",
+    "deezerURL": "deezer",
+    "audibleURL": "audible",
+}
+LINK_LABELS = {
+    "spotify": "Spotify",
+    "apple": "Apple Music",
+    "deezer": "Deezer",
+    "audible": "Audible",
+    "audioteka": "Audioteka",
+    "storytel": "Storytel",
+    "source": "Originalquelle",
+}
+# Nur für diese Keys ergibt ein "fehlt"-Report Sinn (die Marktdienste).
+REQUIRED_LINK_KEYS = ["spotify", "apple", "deezer", "audible"]
+# Erreichbarkeit ja, Titel-Abgleich nein (Sender-Mediathek hat keinen Albumtitel).
+NO_TITLE_CHECK_KEYS = {"source"}
+
+
+def entry_links(entry: dict) -> dict[str, str]:
+    """Vereinigt Legacy-Flachfelder und das V2-links-Objekt zu {key: url}.
+    Ein expliziter links-Eintrag gewinnt gegen das gleichnamige Flachfeld."""
+    merged: dict[str, str] = {}
+    for flat_field, key in LEGACY_URL_FIELDS.items():
+        value = entry.get(flat_field)
+        if value:
+            merged[key] = value
+    for key, value in (entry.get("links") or {}).items():
+        if value and str(value).strip():
+            merged[key] = value
+    return merged
```

## 4. Verifikation (bei der Umsetzung, nicht jetzt)

1. Eine echte heutige Katalogdatei nach V2 umschreiben (eine Serie, `links` +
   `changedAt` + `catalogFormat: 2`), lokal ablegen.
2. `python scripts/check_catalogs.py --sample 3` gegen das lokale `catalogs/`
   laufen lassen, das den umgeschriebenen Katalog und mindestens einen
   unveränderten Legacy-Katalog enthält.
3. Sichtprüfung des Reports:
   - `source`-URL taucht als geprüfter Link auf, **nicht** in „Falsch verknüpfte
     Links".
   - Legacy-Katalog erzeugt denselben Report wie vor der Änderung.
   - `--sample`-Lauf über einen Anthologie-Katalog (nur `slug`, keine `number`)
     wirft keinen `TypeError`/`KeyError`.
4. `upcoming_releases.json` nach einem Schritt-1-Lauf: `feedVersion: 1` gesetzt,
   jede Zeile hat `releaseStatus`, App dekodiert den Feed unverändert
   (`CatalogDataContractTests` + Bestandssuiten grün — bereits in diesem Repo
   abgesichert).
