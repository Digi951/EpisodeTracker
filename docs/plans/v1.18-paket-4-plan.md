## P4-A — `NewsEvent` + `NewsStore`

**Dateien:** `EpisodeTracker/Features/News/NewsEvent.swift` (neu),
`EpisodeTracker/Features/News/NewsStore.swift` (neu),
`EpisodeTrackerTests/NewsStoreTests.swift` (neu).

1. `NewsEvent: Codable, Equatable, Identifiable` — `id: String` (stabil, siehe
   Spec D3), `kind: NewsEventKind` (`newEpisode`/`upcoming`/`dateChanged`/
   `newCatalog`), `catalogID: String?`, `universeName: String`,
   `episodeNumber: Int?`, `slug: String?`, `title: String`,
   `releaseDate: Date?`, `revision: String` (Spec D1), `discoveredAt: Date`,
   `seenAt: Date?`. Decode mit `decodeIfPresent` für alle optionalen Felder.
2. `NewsStoreDocument: Codable` — `schemaVersion: Int`, `hasEstablishedBaseline:
   Bool`, `events: [NewsEvent]`, `lastReconciledRevisions: [String: String]`
   (Ereignis-ID → zuletzt gesehene Revision, überlebt Aufräumen — Spec D5).
3. `NewsStore` (Muster `CatalogCacheStore`): `load() -> NewsStoreDocument`
   (fehlende/korrupte Datei → frisches leeres Dokument, kein Throw nach außen),
   `save(_:) throws` (`Data.write(options: [.atomic])`).
4. Tests: leere Datei → leeres Dokument; Roundtrip erhält alle Felder inkl.
   `seenAt == nil`; absichtlich kaputtes JSON auf der Store-Datei → `load()`
   liefert leeres Dokument statt zu werfen; ein zweiter `save()` überschreibt
   atomar (kein Datenverlust bei simuliertem Absturz zwischen den Schritten —
   Test schreibt zwei Versionen nacheinander und prüft nur die zweite steht).

## P4-B — `NewsReconciler`: Baseline + Deltas

**Dateien:** `EpisodeTracker/Features/News/NewsReconciler.swift` (neu),
`EpisodeTracker/Shared/App/AppDataBootstrapper.swift`,
`EpisodeTrackerTests/NewsReconcilerTests.swift` (neu).

1. `NewsReconciler.establishBaselineIfNeeded(document:deltas:availability:
   upcoming:) -> NewsStoreDocument` — pure: wenn `!document.
   hasEstablishedBaseline`, `lastReconciledRevisions` für jede aktuell
   bekannte Ereignis-ID auf ihre aktuelle Revision setzen, **keine**
   `NewsEvent`s anlegen, `hasEstablishedBaseline = true`.
2. `NewsReconciler.reconcile(document:deltas:availability:upcoming:) ->
   NewsStoreDocument` — pure: für jede Ereignis-ID aus den drei
   Signalquellen (Spec Abschnitt 3) die aktuelle Revision gegen
   `lastReconciledRevisions[id]` vergleichen:
   - kein Eintrag / abweichend UND kein bestehendes `NewsEvent` → neues
     Ereignis mit `discoveredAt = now`, `seenAt = nil`.
   - abweichend UND bestehendes Ereignis vorhanden → siehe P4-C
     (Terminänderung setzt `seenAt = nil`, andere Kinds aktualisieren nur
     Anzeigefelder).
   - unverändert → nichts tun (Idempotenz).
   `lastReconciledRevisions[id]` wird immer auf die aktuelle Revision
   nachgezogen, auch wenn das zugehörige `NewsEvent` später aufgeräumt wird
   (P4-D).
3. `AppDataBootstrapper`: neuer Schritt `reconcileNewsEvents(container:)` —
   liest `CatalogCacheStore().loadCatalogEpisodeDeltas()` /
   `loadNewCatalogAvailability()` / `loadUpcomingReleases()`, ruft
   Baseline-dann-Reconcile, speichert über `NewsStore`. Rein cache-basiert
   (kein Netz-I/O), läuft neben den bestehenden Reconcilern im Bootstrap.
4. Tests: leerer Store + vorhandene Deltas → Baseline, kein Ereignis; zweiter
   Lauf mit unveränderter Revision → weiterhin kein Ereignis; ein neues Delta
   nach der Baseline → genau ein Ereignis; erneuter Lauf ohne neue Rohdaten →
   idempotent (keine Duplikate, `discoveredAt` unverändert).

## P4-C — Terminänderung

**Dateien:** `EpisodeTracker/Features/News/NewsReconciler.swift`,
`EpisodeTrackerTests/NewsReconcilerTests.swift`.

1. Erweiterung von `reconcile(...)`: für `kind == .upcoming`, wenn ein
   bestehendes `NewsEvent` dieselbe Ereignis-ID aber ein **anderes**
   `releaseDate` oder eine andere `revision` aus dem Feed hat, `seenAt = nil`
   setzen (nicht die Zeile duplizieren) und `releaseDate`/`revision`
   aktualisieren.
2. Widerspruchsauflösung: wenn `upcoming`-Rohdaten für dieselbe Ereignis-ID
   mehrfach mit unterschiedlichem `releaseDate` in einem Lauf vorkommen (der
   Feed selbst ist inkonsistent), die **letzte** Zeile aus
   `UpcomingReleasesFeed`/`UpcomingReleasesDocument.releases` gewinnt (Reihen-
   folge im Dokument = Aktualität, analog zur bestehenden Dedup-Regel in
   `CatalogSourceRegistry.deduplicatedManagedSources`), keine Zwischenzeile
   wird geschrieben.
3. Zurückgezogener Termin (Ereignis-ID fällt aus dem aktuellen `upcoming`-
   Datensatz, ohne dass eine `newEpisode`-Zeile mit derselben Identität
   auftaucht): das bestehende `NewsEvent` bleibt unverändert im Store stehen
   (kein automatischer Statuswechsel), nur ein neuer `newEpisode`-Fund
   markiert die Kind-Transition.
4. Tests: Terminverschiebung setzt `seenAt = nil` ohne zweite Zeile;
   zurückgezogener Termin ändert nichts am bestehenden Ereignis;
   widersprüchliche Doppelzeile im selben Lauf → nur die letzte gewinnt, keine
   dritte Zeile.

## P4-D — 90-Tage-Aufräumen

**Dateien:** `EpisodeTracker/Features/News/NewsReconciler.swift`,
`AppDataBootstrapper.swift`, `EpisodeTrackerTests/NewsReconcilerTests.swift`.

1. `NewsReconciler.pruneSeenEvents(document:now:retention: 90 days) ->
   NewsStoreDocument` — pure: entfernt `NewsEvent`s mit `seenAt != nil` und
   `now - seenAt > retention` aus `document.events`.
   `lastReconciledRevisions` bleibt unverändert (Wasserstand überlebt das
   Aufräumen der Anzeigezeile — Spec D5).
2. In `reconcileNewsEvents(container:)` (P4-B) nach dem Reconcile aufrufen,
   vor dem Speichern.
3. Tests: ungesehenes Ereignis übersteht 90+ Tage; gesehenes Ereignis wird nach
   90 Tagen entfernt, mit 89 Tagen nicht; ein aufgeräumtes Ereignis mit seither
   unveränderter Revision erzeugt beim nächsten `reconcile(...)` **kein**
   neues Ereignis (Wasserstand-Test — kombiniert P4-B + P4-D).

## Reihenfolge-Hinweise

- P4-A ist Voraussetzung für alles Weitere (der Store muss existieren).
- P4-B liefert die Baseline/Reconcile-Grundlage, die P4-C (Terminänderung) und
  P4-D (Aufräumen) direkt erweitern — alle drei bleiben in
  `NewsReconciler.swift`, additive Commits auf derselben Datei.
- P4-E/P4-F/P4-G sind UI-lastig und hängen von P4-A–D ab, sind aber
  untereinander weitgehend unabhängig; empfohlene Reihenfolge wie oben, weil
  P4-G die in P4-E/P4-F gebaute Oberfläche voraussetzt.
- Empfehlung: **P4-A → P4-B → P4-C → P4-D → P4-E → P4-F → P4-G → P4-H.**

## Offene Punkte für die Umsetzung

- Genauer Dateiname/Ort für den ersetzten bzw. beibehaltenen
  `UpcomingReleasesSheet`-Code: beim Umsetzen von P4-E entscheiden, ob die
  Datei aufgelöst oder als reine Row-Komponente weiterverwendet wird.
- `NewsOverviewView`-Filterung nach aktivierten Katalogen: heute filtert
  `UpcomingReleasesSheet`/`UpcomingReleasesFeed` implizit über die
  aktivierten Kataloge — genaue Konstruktion der `NewsOverviewOrganizer`-
  Eingabe (welche Filterung passiert wo) beim Umsetzen von P4-B/P4-E prüfen,
  damit deaktivierte Kataloge keine Neuigkeiten mehr erzeugen (§3:
  "Deaktivieren stoppt künftige Aktualisierungen und Neuigkeiten dieser
  Reihe").
- "Katalog ergänzt" vs. "neu erschienen"-Wortwahl (§4.B: Statusänderungen und
  nachträglich ergänzte ältere Werke heißen "Katalog ergänzt") — Textregel in
  P4-E festlegen, sobald die konkreten `CatalogEpisodeDelta`-Fälle vorliegen.
